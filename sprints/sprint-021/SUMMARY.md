# Sprint 021: Authentication: Passkeys, Recovery and a Real Captain Role

## Overview

**Goal**: Replace username-and-password-only login with passkeys as the default, keep passwords as an optional fallback for people who cannot use a passkey, give administrators and server operators a safe way to invite and recover accounts without email, and make the captain role grant real, limited access.

**Duration**: dates TBD

**Status**: Planned

**Programme**: Part of the club-readiness programme (Sprints 019-024). Agreed constraints: BHPLTA clubs only; each club hosts its own instance; the original author has no access to any other club's instance; passkeys by default with passwords as an optional fallback; a real captain role; SQLite only; CourtHive bundled as an opt-in so clubs can run their own championships.

## Focus Areas

1. Passkeys by default; passwords as an optional per-user fallback
2. Account recovery without email: single-use links from the admin UI or the command line
3. Captain role enforced on routes - everything except users, settings and backups
4. Session and login hardening, then an independent security review

## Recommended Models

Each work item's JSON carries a `recommended_model` with the reason. In short:

- **WI-126** - Sonnet 5.5: Small targeted fixes with clear test cases.
- **WI-127** - Opus 5.5: Restructures startup into subcommands and extracts a shared account service; moderate design work.
- **WI-128** - Fable 5.2: Security-critical protocol work where subtle mistakes (origin checks, challenge reuse, enumeration, lockout) are easy to make and hard to spot.
- **WI-129** - Fable 5.2: The recovery path is the weakest point of any passkey system and must be designed together with WI-128.
- **WI-130** - Opus 5.5: Several interacting rules (last-method guard, admin requirement) but a clear specification.
- **WI-131** - Opus 5.5: Several independent hardening changes that each need care with upgrade behaviour.
- **WI-132** - Opus 5.5: Cross-cutting authorisation change over many routes where a missed route is a security bug.
- **WI-133** - Sonnet 5.5: Test authoring against specified behaviour.
- **WI-134** - Fable 5.2: Review quality depends on finding what a careful implementer missed; use the strongest model with fresh context.

## Key Design Decisions

1. Passkeys need a fixed origin, so the instance's public URL becomes a required setting in production (WI-126). Changing a club's domain later invalidates its passkeys; recovery links are the way back and the docs say so.
2. There is no email. An invite or recovery link is generated by an administrator (or by the operator on the server) and handed over however the club likes. Links are single-use, short-lived and stored hashed.
3. The command-line account tool is a subcommand of the main binary so that `docker exec` or SSH on the club's own server is enough - this is the last-resort recovery when every administrator is locked out.
4. Passwords stay as a fallback. A user may have passkeys, a password, or both; an administrator can require passkeys for the admin role.
5. Captain access follows the club's whole-team ethos: every captain sees every team. The role limits administration (users, settings, backups, import configuration), not visibility.
6. Player access by link token is unchanged in this sprint - it is an accepted design with a deliberately small blast radius.
